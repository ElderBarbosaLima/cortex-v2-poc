## What
- `policies/`: `.manifest` (bundle roots `["cortex/policy"]`), `cortex/policy/authz.rego` (placeholder `default allow := false`), `cortex/policy/revision.rego`, tests in `policy_test.rego` (package `cortex.policy_test`), `.regal/config.yaml`.
- `infra/opa/build-bundle.sh` + one-shot `opa-bundle` service: `opa build --revision sha256:<16 hex>` where the hash covers path + content of every policy file and the manifest (tests excluded).
- `opa` service: official `openpolicyagent/opa:1.22.4` (distroless), pinned by digest, `run --server --bundle`, JSON logs, port `127.0.0.1:8181`. It starts only after the bundle is built (`service_completed_successfully`) and is healthy only once the bundle is active.
- Tool services `opa-tools` (`opa test`, `opa check --strict`) and `regal` (0.43.0, pinned digest), both with `network_mode: none`.
- `make test-policies`, `make test-all` (= unit + integration + policies), `make opa-reload`; `make lint` now also runs `opa check --strict` and Regal.
- `docs/discovery.md` §6.7 records the OPA pattern before anything uses it (brief requirement); README has an OPA section.

## Decisions worth a look
- **Healthcheck with OPA itself.** The official image has no shell, and even `-debug` has no `wget`/`nc`. So the check is `opa eval --fail 'http.send({"url": "http://127.0.0.1:8181/health?bundles", ...}).status_code == 200'`. The server keeps the minimal official image. (On Kubernetes this becomes a plain `httpGet` probe.)
- **The `-debug` variant only for the bundle build** (it has `sh` and `sha256sum`). It is also official and pinned by digest. It runs as root only to write into the named volume, with no network.
- **Revision = content hash**, read in policy from `data.system.bundles[_].manifest.revision` of the bundle that owns `cortex/policy`. The policy does not hard-code the bundle's file name, and two bundles claiming the root would be a conflict error, not a silent pick.
- **Data outside the bundle roots.** Tenant trees and grants (issue 13) go to `cortex/tenants/...` through the Data API. OPA refuses writes inside `cortex/policy`, so data can never overwrite policy.
- **Regal exception, with a reason:** `unresolved-reference` is relaxed only for `data.system.bundles`, which OPA fills at runtime from bundle manifests. Rego annotations sit at rule level, because package-level `METADATA` in two files of one package is a compile error.

## Found while testing
- The bundle build first failed on `permission denied`: the OPA images run as uid 1000 and the named volume is root-owned. The one-shot runs as `user: "0"` and `chmod 0644`s the bundle.
- Package-level `METADATA` in both `authz.rego` and `revision.rego` → `rego_type_error: package annotation redeclared`. Moved the annotations to rule level.
