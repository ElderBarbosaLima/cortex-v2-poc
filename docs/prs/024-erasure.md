# PR 024 — Erasure: record lineage and tenant, by crypto-shredding

Branch: `poc/024-erasure` → `main` · Issue: [docs/tasks.md §24](../tasks.md) · Depends on: 23 (merged)

## Two design changes to approve

I found these while building erasure. Without them, erasing a record would leave readable copies behind.

1. **A data key per record, replacing the lineage root's key** (issue 12's choice). Q10's answer allowed either ("DEK por registro (ou por raiz de linhagem)"). With the lineage-root key:
   - a derived record (for example a correction decision) could not be erased without destroying its root;
   - a record derived from several parents stayed readable when any parent but the first was erased, because it was sealed under the first parent's key.

   Now `key_ref = record_id` for every new record, and erasure follows `derived_from` to every descendant instead. The two issue-12 tests that pinned the old behaviour are updated, and their new names say what they check.
2. **The evidence manifest (issue 23) keeps each body sealed under its record's own key.** Before, the bodies sat in clear inside the tenant-encrypted manifest, in an object under Object Lock that cannot be deleted, so erasing a record left its text in the archive.
   - Now each record carries `body_sealed {codec, key_ref, sealed}`, and `evidence.open_pack` rebuilds the pack as served while the keys exist.
   - `pack_sha256` is still the hash of the pack as served, bodies in clear, so integrity checks are unchanged.
   - After a record erasure, the archive returns `body: null` for that record and every other body still opens.

## What
- **`erase-record`** (`app/services/erasure.py`, `make erase-record TENANT= RECORD= BY= REASON=`):
  1. the set to erase is the record plus every record whose `derived_from` names one already in the set, at any position, followed to the end (a recursive SQL query over `memory_record_current`);
  2. each record in the set gets an **`erased` version** (append-only), and its data keys (`record_key` rows) and search rows are deleted;
  3. **packs stay whole**: ids, versions, roles and `body_hash` remain, and `PackRecord` gains `body: null` plus `body_erased: true` for erased bodies. Verify on such a pack holds with `rule_no_longer_approved`;
  4. rows sealed under a shared key before this change pull in every record using that key; the report lists them as `collateral`;
  5. erasing again is harmless: no new versions or keys are destroyed, and the request is logged again.
- **`erase-tenant`** (`make erase-tenant TENANT= BY= REASON= CONFIRM=yes`; it refuses without the confirmation):
  - the tenant's KMS key is disabled with `DisableKey`, then given `ScheduleKeyDeletion` with the 7-day KMS minimum. The probe already showed that `Decrypt` is refused after `ScheduleKeyDeletion`, so `DisableKey` is not a workaround: it is a belt-and-braces step real AWS also supports;
  - every wrapped data key, cached plaintext key and search row of the tenant goes. Every body, pack snapshot and **S3 export** of the tenant stops opening.
- **The cache no longer outlives an erasure.**
  - `KmsKeyService` used to return a cached plaintext key without checking anything. A long-lived process, such as the service or the projector, would still open a record erased by the CLI until it restarted.
  - Now every use checks that the wrapped key row still exists, and the cache only saves the KMS call.
- **Projections never index erased or unreadable bodies.** An `erased` version, or a body whose key is gone, deletes the search row instead of upserting it, so `make reindex` brings nothing back.
- **Erasure log**: migration `010_erasures`, append-only and under RLS. Each row has scope, subject, who asked, the reason and a **report** that lists:
  - the records and the collateral;
  - the keys shredded and the projection rows deleted;
  - the packs and exports affected;
  - for a tenant erasure, the KMS key state.

  The report holds ids and counts only, never text.
- **IAM:** `UseTenantKeys` gains `kms:DisableKey` (`infra/iam/org-brain-service.json`, regenerated by `make provision`).
- **Not in this PR:** an admin HTTP route. The CLI covers "CLI/rota admin" without a new admin identity model.

## Notes
- **The ledger keeps governance metadata in clear after an erasure, by Q10's design.** That covers ids, status, scope, `entities` (opaque canonical keys only, checked at admission), authority and approvals. Legal (D20/APPI) decides whether production needs more.
- **A tenant erasure leaves the ledger rows in place.** No erased versions are appended, because the KEK and data keys are gone and no body opens any more.
